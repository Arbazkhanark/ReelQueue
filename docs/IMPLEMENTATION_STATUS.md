## Security review (session 6, desk review + tests; not a penetration test)

* Tenant isolation: every user-reachable store method filters by the session's `userId`; the id-only methods (`getCycleById`, `getJobAccount`, `getCredentials`, `claim`, `update`, `getJobContext`) are called only from the worker/scheduler or with ids taken from the verified session (grep-checked). OAuth endpoints take no resource ids; the callback authenticates the session itself and binds `state` to userId + a nonce cookie (another logged-in user cannot complete someone else's flow: tested).
* Secrets: tokens are AES-GCM at rest with AAD = userId + provider account id (a ciphertext copied to another row will not decrypt); never returned by the API (asserted); OAuth/SMTP errors are sanitised (no URL, code, token or password); the mailer logs no recipient, link or token; config errors never echo secret values (tested).
* Retries/recovery: provider errors map to ProviderError kinds so transient failures retry and auth failures stop; token refresh uses a per-account lease and compare-and-set, a Meta outage never disconnects an account; retention is idempotent and storage-first.
* Residual risks (not fixed): mail is not durable (no outbox; a crash loses a pending mail, user can re-request); in-memory fallback limiter lets limits multiply by replica count while PostgreSQL is unreachable; the callback `rq_oauth` cookie is `Path=/v1/instagram` and `SameSite=Lax`, which requires the API and web app to be same-site (same registrable domain) in production; no `/v1/admin/*`; no dependency audit was possible (registry blocked); Meta rate-limit/quota behaviour unverified.
